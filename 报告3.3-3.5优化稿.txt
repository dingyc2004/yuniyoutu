系统的信息流可以概括为四条主线。

第一，地图查询信息流：前端首页请求 POI 与天气数据，后端从 pois、weather_snapshots 等集合读取钓点、风险、设施、鱼种和天气信息；若配置了高德 Key，则地图组件加载高德 JS API 展示真实底图、点位和热力，否则使用内置地图 Demo 保证展示稳定。

第二，出钓记录信息流：用户在记录页开竿计时，系统记录开始时间并结合天气信息；位置可通过浏览器定位、地图选点或手动填写。收竿后用户补充鱼获、钓法、饵料、装备和复盘，后端 records 接口将数据写入 records.json，后续用于个人主页、会员报告和记录转帖子。

第三，社区与社交信息流：用户可从记录快速填充发布内容，发布时分别设置内容可见范围和位置公开级别。后端 post_service 在返回公开帖子前执行位置脱敏，避免精确坐标直接进入公开信息流。用户浏览帖子后可进行评论、点赞/收藏、关注作者、发起好友申请，并进入私聊或活动群。

第四，服务与报告信息流：活动和装备模块从 events、event_registrations、equipment、orders 等集合读取数据。用户报名并签到活动后，可生成一条活动出钓记录；装备模块可生成演示订单并模拟支付。报告服务读取用户记录生成统计快照，并结合教程、活动和装备数据给出下一步推荐。

在 GIS 处理上，系统将水域、钓点、规则、记录和社区内容尽量映射到空间对象中。公开分享时，原始坐标不直接作为默认公开信息，系统可按隐藏位置、仅城市、水域模糊或精确位置四种层级展示。在 AI 处理上，系统主要把用户记录和社区内容作为结构化输入，生成复盘建议、标签建议、报告文案和推荐理由。涉及禁钓、限钓、安全提示和水域管理的信息，应以规则数据、来源标记和人工复核状态为准，不能完全交给生成式模型判断。

3.3.5 技术实现边界

第一，当前系统定位为可运行产品 Demo，而不是已经上线的完整商业系统。项目已经能展示地图找点、出钓记录、社区互动、活动报名、装备订单和会员报告等主链路，但登录鉴权、真实支付、对象存储、WebSocket、内容审核、后台管理和高并发数据库仍属于后续正式化工作。

第二，地图与规则信息是出钓决策辅助，不替代官方规定。涉及禁钓、限钓、安全和水域管理的信息，需要展示来源、更新时间和复核状态。当前 data/pois.json 中已有规则和风险说明字段，但仍需后续建立稳定的数据来源和人工复核流程。

第三，AI 在项目中承担解释器和助手角色，适合用于复盘总结、标签建议、教程推荐、服务推荐和报告文案生成，不承诺预测某水域一定有鱼，也不独立承担合规和安全判断。

第四，位置隐私应作为底层数据机制。出钓记录默认作为个人档案保存，社区发布时再单独设置位置公开层级。公开内容默认不应泄露精确坐标，后端返回公开帖子时需要执行位置脱敏，而不能只依赖前端隐藏。

第五，社区内容应区分普通发布内容、记录生成内容和商业合作内容。记录生成内容可以提升可信度，商业合作内容则需要明确标识，避免虚假鱼获、软广和无来源规则信息破坏社区信任。

第六，JSON 文件存储适合课程 Demo 和单机演示，不适合多人并发和长期运营。正式上线前应迁移到数据库，并补充日志、备份、权限校验、异常监控和隐私数据删除能力。

3.5 本章小结

本章从产品功能、产品设计、技术方案和开发计划四个方面说明了“鱼你有图”的实现路径。结合当前项目代码，产品已经形成以首页地图和出钓记录为起点，以社区互动和钓友关系为连接机制，以教程、活动、装备和会员报告为服务延伸的可运行原型。当前版本并不是完整上线系统，而是基于 Vue3 + Vite、FastAPI 和 JSON 数据集合构建的移动端 Web Demo，已经能够演示“地图找点—开竿记录—个人档案—记录转帖子—社区互动—活动/装备服务—会员报告”的主链路。

技术方案上，GIS 负责空间组织、钓点查询、天气与适钓信息展示以及位置隐私模糊化；后端服务负责记录、社区、用户、报告、活动、装备和聊天数据的读写；AI 主要承担复盘建议、标签建议、推荐理由和报告文案等辅助任务，不替代官方规则和安全判断。数据层当前使用 JSON 集合模拟 NoSQL 数据库，便于课程实践和演示迭代，但正式上线前仍需补充真实登录鉴权、数据库、对象存储、WebSocket、支付、后台审核和运维监控等能力。

开发计划以 2026 年 6 月 14 日已有原型为基础，重点不再是从零搭建页面，而是围绕功能闭环、数据持久化、隐私机制、演示稳定性和报告表达准确性进行迭代。团队应优先保证地图查询与出钓记录闭环稳定，再完善社区连接、活动与装备服务，并在报告和答辩中清晰说明“已实现 Demo 能力”和“后续正式化边界”，沿着“先记录，再连接，后服务”的路径推进。
