\section{测试与验收方案}

本项目测试与验收方案以"需求可追踪、功能可复现、指标可度量、缺陷可闭环、成果可交付"为原则。实习要求中明确提出投标文件应结构完整、数据充分、排版规范，并且专业表达要避免口号化形容词；样例技术规范书也要求交付系统测试方案、系统测试用例、系统测试报告，并在正式项目中提交第三方软件测试报告和软件安全风险评估报告。因此，本项目不把测试写成简单的"功能正常即可"，而是按照功能测试、接口测试、数据测试、性能测试、安全测试、兼容性测试、易用性测试、验收测试八类组织，并将每类测试与"鱼你有图"的具体业务链路对应起来。

\subsection{功能测试}

功能测试围绕用户真实出钓流程展开。

第一条主链路为"地图找点—查看钓点详情—查看推荐理由—判断规则风险—开始出钓—收竿记录—生成报告—发布社区"。测试人员需要分别验证地图首页是否能展示附近钓点、钓点卡片是否包含名称、距离、类型、鱼种、收费方式、规则风险和推荐分数，推荐理由是否同时展示鱼情分、合规分、距离分、天气适配分、设施便利分和社交热度分，禁钓、限钓、安全风险是否被优先提示。

第二条主链路为"记录鱼获—绑定地点—填写鱼种、条数、重量、钓法、饵料—保存个人档案—一键生成帖子"。测试人员需要确认记录数据不仅能在当前页面展示，也能进入个人主页统计、会员报告和社区帖子关联。

第三条主链路为"社区浏览—帖子详情—评论点赞收藏—关注好友—私聊或活动群入口"。如果当前版本属于 Demo，则需要明确哪些功能为可操作演示、哪些功能为后续真实持久化功能，避免验收时把演示状态误认为正式能力。

第四条主链路为"教程学习—学习状态保存—报告推荐教程—活动报名—签到—形成活动履历—从活动生成出钓记录"。现有复核文档显示，活动报名、取消报名、现场签到、个人活动履历、教程进度持久化、报告跳转推荐和订单演示闭环已经完成 Demo 层面的完善，但真实支付、退款、商家结算、登录鉴权、WebSocket、对象存储和数据库迁移仍未完成，验收时应据此划分 MVP 验收范围与后续扩展范围。

\subsection{接口测试}

接口测试以 FastAPI 后端为核心，覆盖 POI、帖子、记录、推荐、天气、AI 解释、教程、活动、服务、订单等接口。每个接口至少测试正常请求、缺少参数、非法参数、空结果、权限不足、第三方服务失败和服务器异常七类场景。

对于查询类接口，重点检查分页、筛选、排序和缓存是否正确；对于写入类接口，重点检查字段校验、重复提交、幂等性和数据落库；对于推荐类接口，重点检查禁钓风险是否能够降权或提示，极端天气是否影响推荐结果，商业钓场是否只在设施分上加权而不能覆盖禁钓风险；对于 AI 解释接口，重点检查 AI 解释是否基于规则模型结果生成，不能捏造不存在的钓点、规则、鱼种和天气数据。

接口测试输出包括接口测试用例表、测试数据样例、请求响应截图、异常日志和缺陷记录。对于课程验收，可采用 Postman、Apifox 或 pytest 自动化脚本；对于正式工程，可将接口自动化测试纳入持续集成流程。

\subsection{数据测试}

数据测试重点验证"结构化沉淀"是否成立。鱼你有图的核心价值不是发布普通帖子，而是把一次出钓变成可复用的数据资产。测试时应检查出钓记录、鱼获明细、钓点 POI、天气快照、帖子、教程进度、活动报名、装备订单、会员报告之间的关联是否一致。

例如用户在某钓点完成一次出钓，记录中应保存钓点 ID、时间段、天气快照、鱼种、重量、钓法和可见性设置；如果用户选择发布到社区，帖子应关联 \texttt{record\_id}，而不是只复制一段文本；如果用户设置位置模糊，社区展示不得暴露精确坐标；如果会员报告统计"最高效钓法"，应按单位时间鱼获或单位出钓收益计算，而不能简单按出现次数计算。对于当前仍处于规则版或演示版的统计项，应在测试报告中标注"当前口径"和"后续优化口径"。

数据测试还应包括数据导入、数据导出、备份恢复、重复记录处理、空值处理、坐标越界处理、图片缺失处理和跨端同步冲突处理。

\subsection{性能测试}

性能测试按"课堂演示可用"和"工程上线可用"两级指标设置。

课堂演示级要求为：本地或云端演示环境中，地图首页加载不超过 5 秒，普通接口响应不超过 2 秒，推荐接口在 mock 数据规模下响应不超过 3 秒，发布记录和社区刷新可稳定完成，连续演示 30 分钟不出现服务崩溃。

工程上线级要求为：系统支持至少 100 并发请求，核心交互界面响应时间小于等于 2 秒，模型调度时间小于 3 秒，日志、数据备份和身份认证机制可用；样例技术规范书中也列出了 100 并发请求、交互响应时间小于等于 2 秒、模型调度时间小于 3 秒等指标，作为本项目课程版性能指标的上限。

性能测试场景包括首页 POI 列表查询、钓点详情查询、推荐计算、鱼获发布、图片上传、社区信息流刷新、报告生成和活动报名。测试工具可采用 Locust、JMeter 或 k6，报告中记录并发数、平均响应时间、95 分位响应时间、错误率、CPU/内存占用和数据库连接情况。完成核心接口的轻量压测，并给出可复现实验命令和结果截图。

\subsection{安全测试}

安全测试重点覆盖账号权限、位置隐私、内容安全、第三方密钥和接口滥用。

账号权限方面，正式版本必须由登录令牌确定当前用户，禁止前端直接传入 \texttt{user\_id} 后读取或修改他人记录；当前复核文档也指出，现有请求仍由前端传入 \texttt{user\_id}，正式架构需要登录与刷新令牌、当前用户依赖注入、记录/帖子/私信/报告所有权校验和管理员审核与操作审计。

位置隐私方面，用户可选择精确公开、模糊公开、好友可见或完全隐藏，后端必须根据权限返回不同精度的位置数据，前端不得用隐藏字段保存精确坐标。密钥安全方面，高德、天气、DeepSeek 等 Key 只能保存在后端环境变量，不能进入前端包和公开仓库。内容安全方面，社区帖子、评论、图片和私信需要预留审核、举报、屏蔽和删除机制。接口安全方面，登录、发布、评论、图片上传和 AI 解释接口应设置频率限制，避免恶意刷接口或消耗第三方 API 额度。

正式验收前，应进行漏洞扫描、病毒扫描、基线检查和必要的渗透测试；若作为课程项目，可在测试报告中以"安全自查表 + 风险说明 + 后续加固方案"的方式提交。

\subsection{兼容性与易用性测试}

兼容性与易用性测试覆盖手机屏幕尺寸、浏览器内核、微信小程序容器、安卓与 iOS 行为差异、弱网环境和定位权限拒绝场景。地图类产品最容易出现的问题是定位失败、地图白屏、Key 域名白名单配置错误、手机端滚动与地图拖动冲突、图片上传过慢和键盘遮挡表单。

因此测试用例需要包含：用户拒绝定位时能否手动选择城市或钓点；高德 Key 不可用时是否显示内置演示地图；网络慢时是否显示加载状态；图片过大时是否压缩或提示；发布表单未填必填项时是否明确提示；老人机或小屏设备上按钮是否可点击；教程、报告、活动等页面是否能从底部导航或个人主页顺利到达。易用性验收不以"页面好看"为唯一标准，而以"用户能否在 3 分钟内完成一次从找点到记录的闭环"为主要标准。

\subsection{验收阶段与通过标准}

最终验收分为内部初验、试运行验收和终验三个阶段。

内部初验由项目组完成，目标是保证所有验收用例通过、严重缺陷清零、部署文档可执行、演示数据完整。试运行验收在第 90 天左右进行，目标是完成系统上线试运行，收集老师或同学模拟用户反馈，修复阻断性问题。终验在第 120 天内完成，提交技术投标文件、技术评分表、系统代码、部署说明、测试方案、测试用例、测试报告、操作手册、培训材料、项目总结和演示视频。样例技术规范书明确要求合同签订后 90 个自然日内完成系统上线并开始试运行，120 个自然日内完成终验；本项目实施计划也采用该节奏进行组织。

验收通过标准为：核心业务链路可运行，需求响应表中标注"已实现"的功能均可复现，标注"需补充"的功能均给出实现路线和风险说明，核心接口无阻断缺陷，测试报告与部署说明完整，答辩演示不依赖临时改代码或人工改数据。对于验收不通过项，项目组应形成缺陷清单，明确责任人、修复方式、预计完成时间和复测结论，直至达到课程提交要求。
