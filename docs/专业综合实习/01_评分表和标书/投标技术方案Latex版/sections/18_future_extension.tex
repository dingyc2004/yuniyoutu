\section{后续扩展规划}

本项目后续扩展遵循"先稳主链路，再扩数据层；先做可信记录，再做复杂交易；先做用户价值，再做平台生态"的原则。当前版本已经能够支撑"先记录、再连接、后服务"的核心叙事，包括一键开竿、定位、天气、收竿汇总、鱼获记录、社区关联、活动提醒、活动报名、装备入口和会员报告等演示能力。但是，复核文档也明确指出，真实上线仍需完成登录鉴权、审核、支付、数据库迁移、对象存储、WebSocket 和更完整的数据备份监控。因此，后续扩展不应把所有功能一次性堆上去，而应按数据与安全、地图与规则、社群实时化、商业闭环、公共服务和智能分析六条路线逐步推进。

\subsection{第一阶段：数据与安全底座升级}

当前 JSON 文件适合课程 Demo，但正式多人使用必须迁移到 PostgreSQL/PostGIS、Redis 和对象存储。PostgreSQL/PostGIS 负责保存空间 POI、用户记录、鱼获明细、帖子、活动、订单和报告快照，支持空间索引、范围查询、附近钓点检索和热力统计；Redis 负责缓存天气、热门钓点、推荐结果、登录会话和验证码；对象存储负责图片、视频、头像、报告长图和活动附件。

账号系统方面，引入手机号/微信授权登录、刷新令牌、用户资料、角色权限和资源所有权校验，避免前端传入 \texttt{user\_id} 带来的越权风险。安全方面，引入日志脱敏、操作审计、位置权限分级、数据导出删除机制和备份恢复演练。该阶段的目标不是增加用户看得见的新功能，而是让系统从"可演示"变成"可多人使用、可长期保存、可追责恢复"。

\subsection{第二阶段：地图与钓点数据增强}

鱼你有图的核心壁垒在垂钓语义增强 POI，因此后续需要建立钓点共建、纠错、审核和可信度评分机制。用户可以提交新钓点、补充鱼种、上传环境照片、标记收费信息和规则变化；平台根据用户等级、历史记录真实性、其他用户反馈和管理员审核结果计算数据可信度。禁钓、限钓和安全规则需要建立来源字段、发布日期、适用范围和更新时间，并支持规则变更通知。

热力图也需要从简单活跃度扩展为按鱼种、钓法、季节、时间段和天气条件筛选。例如用户选择"路亚 + 翘嘴 + 傍晚"，系统展示近期相关记录热力，而不是展示所有鱼获热力。对海钓场景，扩展潮汐、浪高、风浪、船次、船长、费用、安全确认和返航时间等字段；对城市近郊野钓场景，扩展停车、夜钓、岸线安全、垃圾点和厕所等字段。该阶段的目标是让地图从"钓点展示"升级为"垂钓决策图层"。

\subsection{第三阶段：社群实时化与内容治理}

当前社区和群聊若主要采用普通 HTTP 刷新，适合演示但不适合真实社交。后续应引入 WebSocket 或消息推送服务，实现私信、活动群聊、未读数、已读状态、消息撤回和图片消息。好友关系从演示用即时通过升级为申请、接受、拒绝、拉黑和举报流程；社区信息流从静态或简单排序升级为关注流、同城流、话题流和钓点关联流；评论、点赞、收藏、关注、举报和屏蔽全部持久化。

内容治理方面，建立帖子审核、图片审核、敏感词过滤、用户举报、管理员处理和违规记录机制。对于涉及禁钓区、危险水域或可能诱导违规捕捞的内容，系统自动添加风险提示或限制传播。该阶段的目标是让结构化社区从"能看能发"升级为"能互动、能沉淀、能治理"。

\subsection{第四阶段：活动与商业闭环正式化}

当前项目已经具备活动报名、取消报名、签到、活动履历、从活动生成出钓记录和订单演示闭环，但真实支付、退款与商家结算仍未接入。后续可将活动模块扩展为同城约钓、钓场比赛、俱乐部活动、新手训练营和亲子垂钓体验，支持报名审核、名额管理、费用支付、签到核验、活动群、活动评价和安全事件反馈。

装备服务扩展为商家认证、商品管理、购物车、订单、支付、退款、售后和佣金结算；装备推荐不只基于广告位，而是基于用户真实记录中的钓法、鱼种、装备使用次数和代表战绩。会员服务从报告生成扩展为月报、年报、生涯报告、钓法效率分析、空军复盘、个人成长建议和同城活动优先报名。该阶段的目标是让商业化建立在真实记录和真实关系之上，而不是简单依赖广告和流量售卖。

\subsection{第五阶段：公共服务与监管协同}

钓鱼不仅是兴趣活动，也涉及生态保护、禁捕禁钓、安全管理和公共水域秩序。后续平台可以为地方水域管理方、渔政部门、钓场经营主体和文旅单位提供轻量化管理工具。例如公共水域规则可视化、违规高风险区域提醒、文明垂钓积分、钓点垃圾反馈、安全隐患上报、活动备案、钓场经营数据看板等。

对用户端，平台只展示通俗易懂的"可钓、限钓、禁钓、注意安全"提示；对管理端，平台提供规则配置、公告发布、用户反馈处理和空间热力分析。该方向需要严格处理数据合规和政府合作边界，不应在课程版本中承诺已经具备正式监管能力，而应作为后续可拓展方向。其价值在于将"能不能钓"的用户需求与"如何规范休闲垂钓"的公共管理需求连接起来。

\subsection{第六阶段：智能分析与算法优化}

当前推荐以规则模型为主，AI 做解释，这是 MVP 阶段正确选择。后续当记录数据积累后，可以逐步引入更精细的个性化推荐和因果分析，但仍需保持可解释和可控。例如基于用户历史记录预测不同天气、时段、水域类型下的上鱼概率；基于同城相似用户发现适合新手的钓点；基于空军记录推荐调整钓法、饵料或时间段；基于装备使用记录评估装备适配场景；基于报告结果推荐教程、活动和服务。

算法评估指标可以包括推荐点击率、出钓后记录率、用户采纳率、推荐后上鱼率、空军复盘完成率和报告转化率。AI 解释仍然只解释结构化结果，不直接编造事实。对于模型偏差，需要允许用户反馈"推荐不准、规则错误、钓点关闭、鱼种不符"，并将反馈进入数据更新流程。该阶段的目标是把"经验判断"逐步升级为"数据驱动但可解释的垂钓辅助决策"。

\subsection{版本规划}

后续扩展的时间安排建议分为三个版本。V1.0 面向课程验收和小范围演示，目标是稳定主链路，完成地图、推荐、记录、社区、报告、活动和订单演示，提供部署说明、测试报告和演示数据。V1.5 面向小范围真实用户试点，目标是完成登录鉴权、数据库迁移、对象存储、真实高德服务、位置隐私、内容举报和基础监控，选择武汉或长江经济带某一城市进行数据验证。V2.0 面向商业化验证，目标是完善同城活动、会员报告、教程推荐、商家认证、订单支付和活动安全管理。V3.0 面向平台生态，目标是形成钓点共建审核体系、监管协同接口、B 端经营工具和跨城市复制能力。每个版本都应有明确的验收指标，避免用"持续优化"代替具体计划。

需要强调的是，后续扩展不是对本期投标范围的无限追加。按照工程投标文件的写法，本期承诺应聚焦 MVP 和课堂验收要求，后续规划只说明技术路线、扩展边界和演进方向。对真实支付、正式监管合作、大规模数据库、第三方安全测评、CNAS 测试报告等能力，如果课程项目无法实际完成，应表述为"正式工程化阶段实施"，不能写成当前已具备。这样的表达既能体现项目想象力，也能保持投标文件的真实性和可验收性。
