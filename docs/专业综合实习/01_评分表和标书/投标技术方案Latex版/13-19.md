# 第3份：工程落地与支撑

## 13 部署与运行方案

本项目“鱼你有图”拟采用“移动端应用 + 后端服务 + 空间数据服务 + 第三方能力封装 + 运维监控”的部署模式。平台面向钓鱼爱好者提供地图找点、禁钓规则提示、鱼情推荐、鱼获记录、社区分享、教程学习、活动报名和会员报告等服务，因此部署方案不能只满足页面可访问，还必须保证空间位置服务稳定、用户出钓记录可持续保存、第三方接口调用安全、异常情况下可降级运行。根据现有开发设计，项目当前采用 Vue3/Uni-app 作为移动端与小程序端开发基础，后端采用 FastAPI 提供统一 API，地图能力接入高德 JS API，天气、POI、AI 解释等能力通过后端进行封装，第三方密钥不得写死在前端代码中，推荐排序由后端规则模型先完成，AI 只负责解释生成。该责任边界能够降低密钥泄露风险，也能避免 AI 输出直接影响业务排序结果。

正式部署时，系统划分为开发环境、测试环境、预生产环境和生产环境四类。开发环境用于小组成员本地调试，前端通过 `npm install` 和 `npm run dev` 启动，后端通过 Python 3.11、`requirements.txt` 和 `uvicorn app.main:app` 启动，环境变量统一放置在 `.env` 文件中；测试环境用于接口联调、功能测试和验收前缺陷修复；预生产环境用于模拟真实域名、真实地图 Key、真实对象存储和生产级数据库配置；生产环境用于正式运行。现有项目文档中已说明，当前 MVP 阶段根目录 `data/` 使用 JSON 模拟 NoSQL 数据库，每个 `.json` 对应一个集合，每个 `.schema.json` 对应集合字段说明；但正式运行阶段，JSON 文件只作为初始化演示数据和导入模板，不再承担多人并发写入职责。正式生产环境建议采用 PostgreSQL/PostGIS 存储钓点、鱼获、用户、帖子、活动、订单等结构化数据，采用 Redis 进行热点 POI、天气摘要、推荐结果和登录会话缓存，采用对象存储保存鱼获图片、视频、报告长图和用户头像，采用 Nginx 进行静态资源托管、HTTPS 终止、反向代理和 gzip/brotli 压缩。

生产部署的基本拓扑为：用户通过微信小程序、H5 或 App 访问前端页面；前端页面访问网关域名；Nginx 将 `/api` 请求转发至 FastAPI 服务，将静态资源请求转发至前端构建产物，将图片与视频访问转发至对象存储或 CDN；FastAPI 负责业务接口、权限校验、推荐计算、AI 解释封装、地图配置下发和第三方接口代理；数据库负责长期数据沉淀；Redis 负责缓存和异步任务状态；日志系统记录接口调用、异常堆栈、用户关键操作与第三方调用结果。第三方能力包括高德地图、高德 Web 服务、天气服务、日出日落/潮汐数据、DeepSeek 或其他大模型解释接口。所有第三方 Key 均通过服务端环境变量配置，并由后端提供受控接口给前端使用，不允许出现在 Git 仓库、前端打包文件、公开截图和测试报告中。现有开发设计已经明确，高德 JS API Key 由后端 `/api/amap/config` 提供，Web 服务 Key 只放在后端环境变量中，DeepSeek Key 通过 `DEEPSEEK_API_KEY` 配置，当前 AI 接口可 mock，后续可切换真实解释生成。

为了满足课程实习中“工程交付”的要求，本项目部署不以“能跑”为最低标准，而以“可安装、可配置、可回滚、可观测、可交接”为目标。后端服务采用容器化部署时，可将 FastAPI、Nginx、PostgreSQL、Redis、对象存储适配器分别作为服务模块管理；如果课程验收环境不要求 Docker，则提供非容器化部署脚本，保证评审人员可在 Windows 或 Linux 环境下按部署说明完成启动。前端构建采用 `npm run build` 输出静态资源，后端以 `uvicorn` 或 `gunicorn + uvicorn worker` 方式运行，生产模式关闭调试日志，启用访问日志、错误日志和接口耗时记录。对于地图、推荐、记录、社区、报告、活动等核心接口，均设置统一超时策略和错误返回格式。例如地图 POI 请求失败时，前端展示“地图服务暂时不可用，可查看演示钓点列表”；AI 解释失败时，系统仍返回规则模型排序结果，只将解释部分标记为“暂未生成”；天气接口失败时，采用最近一次缓存天气或提示用户刷新，不影响用户继续记录鱼获。这样的降级设计符合本项目 MVP 边界，也避免把第三方服务不稳定直接转化为平台不可用。

系统运行期间，平台应建立“应用监控、日志监控、数据备份、异常响应、版本发布”五类运行机制。应用监控方面，记录 API 平均响应时间、95 分位响应时间、错误率、第三方接口失败率、数据库连接池状态、Redis 命中率、对象存储上传成功率和前端白屏率。对于地图首页、钓点详情、推荐接口、发布接口、社区信息流、报告生成、活动报名和订单演示等核心链路，设置单独指标。日志监控方面，按用户操作日志、接口执行日志、异常日志、第三方调用日志和安全审计日志分类保存；日志不得记录明文密码、完整第三方密钥和用户精确位置明文，必要时对位置坐标进行权限隔离与脱敏显示。数据备份方面，数据库每日增量备份、每周全量备份，备份保留不少于 30 天；对象存储开启版本管理或回收站机制；关键配置文件和 `.env.example` 纳入版本管理，真实 `.env` 不入库。恢复演练方面，项目上线前至少完成一次“数据库恢复 + 图片访问恢复 + 服务重启”的演练，保证误删数据或服务故障后可在约定时间内恢复核心功能。

版本发布采用“需求冻结—测试构建—预生产验证—生产发布—观察回滚”的流程。每次发布前，产品经理确认需求范围，后端负责人确认数据库迁移脚本，前端负责人确认页面构建产物，测试负责人确认回归测试结果，项目经理确认发布窗口。发布后 30 分钟内重点观察登录、地图、推荐、发布、社区、记录和报告生成接口；若出现核心功能不可用、数据写入异常、用户无法登录、第三方 Key 配置错误或响应时间明显劣化，则启动回滚。回滚内容包括前端静态包回退、后端镜像回退、数据库迁移回滚或兼容脚本处理。对于数据库字段升级，采用向后兼容原则，新增字段优先设置默认值，不在同一版本中删除旧字段；前端接口调用先保留兼容层，再逐步切换到新字段。现有协作规范中也强调“先改设计书，再改接口，再改页面”“接口变更必须先对齐返回结构”“新增字段先保证兼容，不要一次性删除旧字段”，该原则将被纳入部署发布制度。

运行支撑方面，本项目承诺提供部署说明、系统操作手册、管理员配置手册、接口说明、数据库初始化脚本、测试账号、演示数据和常见问题清单。针对课堂实习场景，可提供本地单机部署和在线演示部署两套方式：本地单机部署便于老师检查项目代码与架构，在线演示部署便于答辩展示真实交互。针对正式化工程场景，可提供云服务器部署、域名备案说明、HTTPS 证书配置、数据库备份策略和对象存储配置说明。运行维护期间，平台支持按模块关闭非核心功能，例如真实支付未接入时，装备订单仅保留模拟下单与取消；AI 接口费用超限时，推荐排序继续运行，仅暂停解释生成；活动服务未开放时，地图、记录、社区和报告功能仍可独立运行。通过模块化部署和降级策略，系统能够在课程验收、演示竞赛和后续商业迭代之间保持一致的技术路线，避免为了演示临时写死逻辑，也避免在 MVP 阶段承诺超过团队开发能力的复杂能力。

## 14 测试与验收方案

本项目测试与验收方案以“需求可追踪、功能可复现、指标可度量、缺陷可闭环、成果可交付”为原则。实习要求中明确提出投标文件应结构完整、数据充分、排版规范，并且专业表达要避免口号化形容词；样例技术规范书也要求交付系统测试方案、系统测试用例、系统测试报告，并在正式项目中提交第三方软件测试报告和软件安全风险评估报告。  因此，本项目不把测试写成简单的“功能正常即可”，而是按照功能测试、接口测试、数据测试、性能测试、安全测试、兼容性测试、易用性测试、验收测试八类组织，并将每类测试与“鱼你有图”的具体业务链路对应起来。

功能测试围绕用户真实出钓流程展开。第一条主链路为“地图找点—查看钓点详情—查看推荐理由—判断规则风险—开始出钓—收竿记录—生成报告—发布社区”。测试人员需要分别验证地图首页是否能展示附近钓点、钓点卡片是否包含名称、距离、类型、鱼种、收费方式、规则风险和推荐分数，推荐理由是否同时展示鱼情分、合规分、距离分、天气适配分、设施便利分和社交热度分，禁钓、限钓、安全风险是否被优先提示。第二条主链路为“记录鱼获—绑定地点—填写鱼种、条数、重量、钓法、饵料—保存个人档案—一键生成帖子”。测试人员需要确认记录数据不仅能在当前页面展示，也能进入个人主页统计、会员报告和社区帖子关联。第三条主链路为“社区浏览—帖子详情—评论点赞收藏—关注好友—私聊或活动群入口”。如果当前版本属于 Demo，则需要明确哪些功能为可操作演示、哪些功能为后续真实持久化功能，避免验收时把演示状态误认为正式能力。第四条主链路为“教程学习—学习状态保存—报告推荐教程—活动报名—签到—形成活动履历—从活动生成出钓记录”。现有复核文档显示，活动报名、取消报名、现场签到、个人活动履历、教程进度持久化、报告跳转推荐和订单演示闭环已经完成 Demo 层面的完善，但真实支付、退款、商家结算、登录鉴权、WebSocket、对象存储和数据库迁移仍未完成，验收时应据此划分 MVP 验收范围与后续扩展范围。

接口测试以 FastAPI 后端为核心，覆盖 POI、帖子、记录、推荐、天气、AI 解释、教程、活动、服务、订单等接口。每个接口至少测试正常请求、缺少参数、非法参数、空结果、权限不足、第三方服务失败和服务器异常七类场景。对于查询类接口，重点检查分页、筛选、排序和缓存是否正确；对于写入类接口，重点检查字段校验、重复提交、幂等性和数据落库；对于推荐类接口，重点检查禁钓风险是否能够降权或提示，极端天气是否影响推荐结果，商业钓场是否只在设施分上加权而不能覆盖禁钓风险；对于 AI 解释接口，重点检查 AI 解释是否基于规则模型结果生成，不能捏造不存在的钓点、规则、鱼种和天气数据。接口测试输出包括接口测试用例表、测试数据样例、请求响应截图、异常日志和缺陷记录。对于课程验收，可采用 Postman、Apifox 或 pytest 自动化脚本；对于正式工程，可将接口自动化测试纳入持续集成流程。

数据测试重点验证“结构化沉淀”是否成立。鱼你有图的核心价值不是发布普通帖子，而是把一次出钓变成可复用的数据资产。测试时应检查出钓记录、鱼获明细、钓点 POI、天气快照、帖子、教程进度、活动报名、装备订单、会员报告之间的关联是否一致。例如用户在某钓点完成一次出钓，记录中应保存钓点 ID、时间段、天气快照、鱼种、重量、钓法和可见性设置；如果用户选择发布到社区，帖子应关联 `record_id`，而不是只复制一段文本；如果用户设置位置模糊，社区展示不得暴露精确坐标；如果会员报告统计“最高效钓法”，应按单位时间鱼获或单位出钓收益计算，而不能简单按出现次数计算。对于当前仍处于规则版或演示版的统计项，应在测试报告中标注“当前口径”和“后续优化口径”。数据测试还应包括数据导入、数据导出、备份恢复、重复记录处理、空值处理、坐标越界处理、图片缺失处理和跨端同步冲突处理。

性能测试按“课堂演示可用”和“工程上线可用”两级指标设置。课堂演示级要求为：本地或云端演示环境中，地图首页加载不超过 5 秒，普通接口响应不超过 2 秒，推荐接口在 mock 数据规模下响应不超过 3 秒，发布记录和社区刷新可稳定完成，连续演示 30 分钟不出现服务崩溃。工程上线级要求为：系统支持至少 100 并发请求，核心交互界面响应时间小于等于 2 秒，模型调度时间小于 3 秒，日志、数据备份和身份认证机制可用；样例技术规范书中也列出了 100 并发请求、交互响应时间小于等于 2 秒、模型调度时间小于 3 秒等指标，可作为本项目课程版性能指标的参考上限。 性能测试场景包括首页 POI 列表查询、钓点详情查询、推荐计算、鱼获发布、图片上传、社区信息流刷新、报告生成和活动报名。测试工具可采用 Locust、JMeter 或 k6，报告中记录并发数、平均响应时间、95 分位响应时间、错误率、CPU/内存占用和数据库连接情况。若课程时间有限，至少完成核心接口的轻量压测，并给出可复现实验命令和结果截图。

安全测试重点覆盖账号权限、位置隐私、内容安全、第三方密钥和接口滥用。账号权限方面，正式版本必须由登录令牌确定当前用户，禁止前端直接传入 `user_id` 后读取或修改他人记录；当前复核文档也指出，现有请求仍由前端传入 `user_id`，正式架构需要登录与刷新令牌、当前用户依赖注入、记录/帖子/私信/报告所有权校验和管理员审核与操作审计。 位置隐私方面，用户可选择精确公开、模糊公开、好友可见或完全隐藏，后端必须根据权限返回不同精度的位置数据，前端不得用隐藏字段保存精确坐标。密钥安全方面，高德、天气、DeepSeek 等 Key 只能保存在后端环境变量，不能进入前端包和公开仓库。内容安全方面，社区帖子、评论、图片和私信需要预留审核、举报、屏蔽和删除机制。接口安全方面，登录、发布、评论、图片上传和 AI 解释接口应设置频率限制，避免恶意刷接口或消耗第三方 API 额度。正式验收前，应进行漏洞扫描、病毒扫描、基线检查和必要的渗透测试；若作为课程项目，可在测试报告中以“安全自查表 + 风险说明 + 后续加固方案”的方式提交。

兼容性与易用性测试覆盖手机屏幕尺寸、浏览器内核、微信小程序容器、安卓与 iOS 行为差异、弱网环境和定位权限拒绝场景。地图类产品最容易出现的问题是定位失败、地图白屏、Key 域名白名单配置错误、手机端滚动与地图拖动冲突、图片上传过慢和键盘遮挡表单。因此测试用例需要包含：用户拒绝定位时能否手动选择城市或钓点；高德 Key 不可用时是否显示内置演示地图；网络慢时是否显示加载状态；图片过大时是否压缩或提示；发布表单未填必填项时是否明确提示；老人机或小屏设备上按钮是否可点击；教程、报告、活动等页面是否能从底部导航或个人主页顺利到达。易用性验收不以“页面好看”为唯一标准，而以“用户能否在 3 分钟内完成一次从找点到记录的闭环”为主要标准。

最终验收分为内部初验、试运行验收和终验三个阶段。内部初验由项目组完成，目标是保证所有验收用例通过、严重缺陷清零、部署文档可执行、演示数据完整。试运行验收在第 90 天左右进行，目标是完成系统上线试运行，收集老师或同学模拟用户反馈，修复阻断性问题。终验在第 120 天内完成，提交技术投标文件、技术评分表、系统代码、部署说明、测试方案、测试用例、测试报告、操作手册、培训材料、项目总结和演示视频。样例技术规范书明确要求合同签订后 90 个自然日内完成系统上线并开始试运行，120 个自然日内完成终验；本项目实施计划也采用该节奏进行组织。 验收通过标准为：核心业务链路可运行，需求响应表中标注“已实现”的功能均可复现，标注“需补充”的功能均给出实现路线和风险说明，核心接口无阻断缺陷，测试报告与部署说明完整，答辩演示不依赖临时改代码或人工改数据。对于验收不通过项，项目组应形成缺陷清单，明确责任人、修复方式、预计完成时间和复测结论，直至达到课程提交要求。

## 15 核心优势与创新点

“鱼你有图”的核心优势不在于简单叠加地图、天气、社区和 AI，而在于围绕钓鱼场景形成“垂钓语义增强 POI—个人出钓档案—结构化社区—数据驱动服务”的闭环。现有产品计划书已经明确，本项目面向钓鱼爱好者，围绕“去哪钓、能不能钓、有没有鱼、如何分享鱼获”等问题，整合鱼获照片、POI 系统、禁渔区查询、鱼情预测和区域钓鱼竞赛，打造兼具社群趣味和实用价值的 GIS 智能平台。 与传统地图相比，本项目不是重做底图，而是在成熟地图能力之上叠加垂钓专题语义；与普通社区相比，本项目不是让用户只发图文，而是把鱼获照片与地点、时间、天气、鱼种、钓法、装备和复盘绑定；与单点天气工具相比，本项目不是只告诉用户“今天气温多少”，而是把天气、钓点、规则、历史鱼获和个人偏好转化为可解释的出钓建议。

第一项优势是垂钓语义增强 POI。传统地图平台可以回答“某个水库在哪里、怎么去”，但很难回答“这里能不能钓、适合什么鱼种、最近有没有人上鱼、是否收费、夜钓是否安全、是否处于禁钓或限钓范围”。鱼你有图在 POI 数据模型中增加水域类型、收费方式、常见鱼种、钓法适配、停车便利、夜钓条件、管理单位、规则风险、近期鱼获、钓友评价和更新时间等字段，使钓点从普通地理点变成面向垂钓决策的专题对象。该创新点具有明确工程价值：一方面，用户能够在地图页直接筛选“野钓、钓场、免费、夜钓、路亚、可停车”等条件；另一方面，推荐模型能够基于 POI 字段计算鱼情分、合规分、距离分、天气适配分、设施便利分和社交热度分。产品计划书中也提出，“垂钓语义增强 POI”是项目核心数据壁垒，包括水域类型、管理单位、收费方式、禁渔期规则、常见鱼种和历史鱼获密度等信息。

第二项优势是个人出钓档案。钓鱼用户的真实需求并不止于“发一张鱼获照片”，还包括回看自己去过哪里、钓了多久、什么天气更容易上鱼、哪种钓法更适合自己、哪些装备带来了更好体验。鱼你有图将一次出钓拆解为开始时间、结束时间、钓点、轨迹、天气快照、鱼种、数量、重量、钓法、饵料、装备、照片、笔记和复盘等字段，形成可统计、可检索、可生成报告的个人数据资产。现有项目复核显示，当前版本已经能演示“先记录”的主链路，包括一键开竿计时、定位、天气和收竿汇总，钓鱼过程中逐条记录鱼种、重量、长度和上鱼时间，收竿后可选择发布到社区，个人主页汇总出钓数据并生成月报、年报和生涯报告。 这意味着平台不是一次性工具，而是随着用户记录次数增加不断提升价值的长期档案系统。

第三项优势是结构化社区。普通短视频和图文社区可以满足“晒鱼获”的即时表达，但其内容往往难以沉淀为可复用知识。鱼你有图要求社区帖子尽可能关联真实出钓记录，帖子不只是标题、正文和图片，还包含钓点、鱼种、钓法、天气、时间段、位置可见性、记录 ID 和复盘标签。这样做的好处是，一条帖子既是社交内容，也是钓点知识更新来源；一次空军复盘既能表达情绪，也能帮助其他用户判断水情和钓法；一次装备测评既能形成内容消费，也能关联真实使用次数和代表战绩。产品计划书也指出，鱼获照片与地点、时间、天气、鱼种、钓法、装备和用户评价绑定后，一次分享同时产生社交价值和数据价值。 与纯社区相比，这种结构化社区更适合后续做钓点可信度、鱼情热力、教程推荐、活动组织和装备服务。

第四项优势是“规则优先、AI 解释”的推荐机制。当前很多产品容易把 AI 作为宣传重点，但在钓鱼场景中，真正不能出错的是禁钓、限钓、安全风险、极端天气和位置隐私。如果 AI 直接决定推荐，很容易出现解释好听但结论不可靠的问题。因此本项目采用后端规则模型先排序、AI 只解释的技术路线。开发设计书明确提出，推荐排序由后端规则模型完成，AI 只做解释；规则原则包括禁钓、限钓、安全风险必须优先提示，极端天气优先降权，近距离不等于高分，必须结合鱼情和合规判断，商业钓场可在设施分上适当加权但不能覆盖禁钓风险。 这种机制的创新在于，它把 AI 放在“降低理解成本”的位置，而不是把 AI 放在“替代规则判断”的位置，既保留智能体验，又降低错误推荐带来的安全与合规风险。

第五项优势是位置隐私与知识共享之间的平衡。钓鱼用户既有分享欲，也有保护钓点的需求。野钓点一旦被精确公开，可能导致过度聚集、垃圾污染、资源破坏和用户不愿分享。因此鱼你有图在发布和社区设计中引入位置可见性，支持精确公开、模糊公开、好友可见和完全隐藏等模式。平台可以在不暴露精确坐标的前提下，保留城市、区县、水域类型、天气、鱼种和钓法等统计信息，让用户既能表达经验，又不必担心私密钓点被完全公开。该设计不仅提升用户信任，也为平台后续与公共管理部门、钓场经营者和社区活动组织者合作提供合规基础。当前复核文档也将“社区帖子可关联真实出钓记录，并分别设置内容权限和位置权限”列为已经能支撑的核心叙事之一。

第六项优势是商业服务与真实记录的连接。鱼你有图的商业闭环不是单纯卖广告，而是基于用户长期记录形成服务推荐。会员报告可以发现用户的高频钓点、常用钓法、空军时段、目标鱼种和装备偏好；教程可以根据用户短板推荐；活动可以根据同城用户和钓法兴趣组织；装备服务可以展示真实使用次数和代表战绩，而不是只依赖商家宣传。商业 PPT 中将项目定位为“钓鱼者的个人出钓档案与专属兴趣社区”，并提出以低门槛记录形成个人数据资产，以结构化社区形成关系网络，再通过个性化会员报告、活动组织、教程内容和装备交易实现商业化。 这种商业模式与技术结构一致：没有记录，就没有报告；没有结构化社区，就没有可信内容；没有可信内容，就难以支撑活动和装备服务。

第七项优势是 MVP 可落地性。很多创新项目容易陷入“大而全”，最终无法交付。本项目现有开发设计明确划定 MVP 范围，只做地图首页、钓点 POI 列表与详情、POI 规则推荐、鱼获/空军发布、社区鱼获流、教程页和 AI 推荐解释，不在当前阶段承诺完整会员系统、赛事系统、复杂商户系统、遥感识别、正式禁渔区数据合作、完整数据库和权限体系、统一登录和多端账号打通。 这种边界意识本身就是工程优势：课堂验收阶段优先跑通“地图找点—详情—推荐解释—发布—社区展示”闭环，后续再逐步迁移数据库、接入真实高德 POI、增加用户系统、完善收藏关注评论点赞、引入禁渔区数据和更精细的 AI 复盘。项目既有创新表达，也有可交付路径，能够避免“概念很大、系统不可用”的问题。

综合来看，鱼你有图的创新不是孤立功能，而是围绕垂钓这一垂直场景完成空间数据、用户记录、社区内容、规则推荐和商业服务的系统组织。其可量化优势可以通过以下指标验证：一次出钓记录字段完整率、帖子与真实记录关联比例、推荐接口响应时间、禁钓风险提示召回率、用户完成一次记录所需步骤数、报告生成成功率、活动报名到签到转化率、教程推荐点击率、装备卡真实记录关联比例。相较于“好看”“智能”“有趣”等口号化表达，这些指标能够直接进入技术评分表和验收测试表，符合实习对客观可量化、专业表达和工程交付意识的要求。

## 16 项目实施计划

本项目实施计划采用 120 个自然日完成终验的总体节奏，并设置需求分析、系统设计、核心开发、联调测试、试运行优化、终验交付六个阶段。样例技术规范书要求合同签订后 30 个自然日内完成系统需求分析和框图设计，90 个自然日内完成系统上线并开始试运行，120 个自然日内完成终验；本项目以该节奏作为课程技术投标文件的进度框架，使计划既符合真实招投标文档语言，也便于老师检查阶段成果。 由于本项目已有产品计划、功能设计、开发设计和差距复核文档，实施重点不是从零开始构思，而是将已有 Demo 整理为可部署、可测试、可验收、可交接的工程版本。

第 1—10 天为项目启动与范围确认阶段。项目组召开启动会，明确项目目标、验收口径、人员分工、沟通机制、代码仓库、文档目录、命名规范和提交节奏。产品负责人整理需求清单，将前两份投标文件中的项目概述、需求分析、总体技术方案、系统架构、业务流程、功能响应表、数据模型、推荐模型、技术选型、安全隐私等内容转化为待开发和待验证任务。项目经理建立需求跟踪表，字段包括需求编号、需求名称、来源章节、优先级、实现状态、负责人、接口依赖、测试用例、验收证据和备注。技术负责人完成当前代码审查，确认哪些功能已经实现、哪些功能属于 Demo、哪些功能需要补齐，特别关注真实高德凭据、登录鉴权、数据库迁移、活动闭环、订单闭环、测试覆盖、部署说明等风险点。该阶段输出《项目启动记录》《需求跟踪表》《人员分工表》《版本计划表》和《风险初始清单》。

第 11—30 天为需求分析与总体设计阶段。该阶段完成系统需求规格说明、原型完善、概要设计、数据库设计、接口设计和部署设计。产品负责人根据用户主链路梳理页面，包括地图首页、钓点详情、发布页、社区页、教程页、我的页、会员报告、活动服务、装备服务和消息入口；后端负责人整理 API，包括 POI 查询、钓点详情、推荐排序、天气快照、帖子列表、帖子发布、出钓记录、会员报告、教程进度、活动报名、活动签到、订单演示等；数据负责人统一数据模型，明确 POI、Record、Catch、Post、User、Report、TutorialProgress、Activity、Order 等对象的字段、主键、外键或关联字段；安全负责人设计权限、位置隐私、内容审核和密钥管理方案。该阶段必须完成系统架构图、数据流程图、业务流程图和接口清单，保证后续开发不会边做边改方向。对于当前尚未纳入 MVP 的完整支付、正式商户后台、监管端大屏、遥感识别等能力，应在需求规格中明确列入“后续扩展”，不纳入本期验收，以控制范围蔓延。

第 31—55 天为后端与数据基础开发阶段。后端团队优先完成 FastAPI 结构整理、Pydantic Schema 校验、统一错误返回、日志中间件、环境变量读取、第三方服务封装和数据持久化改造。若课程时间允许，优先将 JSON 文件存储迁移到 SQLite 或 PostgreSQL；若时间有限，则至少保证 JSON 数据写入有备份机制、字段有 schema 说明、演示数据稳定。推荐服务在本阶段完成规则模型接口，输出总分、分项分、推荐原因、风险提示和关联 POI 数据；AI 解释服务在本阶段完成 mock 与真实接口双模式，保证无 Key 时可演示，有 Key 时可切换真实生成。记录服务完成开竿、收竿、鱼获明细、天气快照、图片字段和社区发布关联；活动服务完成列表、报名、取消报名、签到、履历和从活动生成出钓记录；教程服务完成收藏、学习中、完成状态写入；订单演示服务完成下单、订单列表、模拟支付和取消订单。现有复核文档显示，这些 Demo 闭环已有部分完善结果，实施阶段需要将其整理为稳定接口和测试用例，而不是仅停留在页面演示。

第 46—75 天为前端页面与交互开发阶段，与后端开发存在部分并行。前端团队围绕“地图找点—详情—推荐—记录—报告—社区—服务”的主链路进行页面完善。地图页需要支持搜索、筛选、POI 标记、钓点卡片、天气摘要和推荐提示；钓点详情页需要展示基本信息、鱼情分、合规分、距离分、天气适配分、设施便利分、社交热度分和风险提示；发布页需要支持鱼获、空军、探点和教程心得等类型，至少保证鱼种、数量、重量、钓法、饵料、地点、天气和位置权限可录入；社区页需要展示推荐流、同城流、话题流、帖子详情、点赞评论收藏入口；我的页需要展示个人记录、收藏、战绩摘要、报告生成和报告推荐；服务页需要展示活动、群聊和装备入口。前端还要处理加载状态、错误状态、空状态和弱网状态，避免演示时只要一个接口失败就出现白屏。对于高德底图不可用的情况，保留内置演示地图或钓点列表，保证课堂展示不受 Key 配置影响。

第 76—90 天为系统联调与上线试运行阶段。该阶段将前后端部署到测试环境，使用统一域名和真实或模拟第三方配置进行联调。项目组按验收主链路执行端到端测试，包括新用户进入地图、查看钓点、获得推荐、开始记录、收竿保存、生成报告、发布社区、查看教程、报名活动、签到、形成活动履历、下单装备演示。测试负责人每天汇总缺陷，按严重程度分为阻断、严重、一般和建议四类；阻断缺陷必须当天或次日修复，严重缺陷必须在试运行结束前清零，一般缺陷可纳入终验前优化，建议类缺陷进入后续版本。项目经理在第 90 天形成《试运行报告》，内容包括已完成功能、待优化功能、测试数据、缺陷统计、性能结果、安全自查和下一阶段计划。样例技术规范书中要求 90 天上线试运行，该阶段就是对该节点的响应。

第 91—105 天为质量加固与验收准备阶段。该阶段重点不是继续扩功能，而是补齐测试、文档、安全和部署。测试方面完成单元测试、接口测试、端到端测试、性能测试和兼容性测试；文档方面完成部署说明、用户手册、管理员手册、接口文档、数据库说明、测试方案、测试用例、测试报告和培训材料；安全方面完成密钥检查、权限检查、位置隐私检查、XSS/SQL 注入基础检查、上传文件类型检查、日志脱敏检查和备份恢复演练；部署方面完成本地部署脚本、云端部署说明、`.env.example`、初始化数据和演示账号。该阶段还需要完成一次正式彩排，按答辩顺序演示，不允许现场临时修改数据；如果某功能仍未稳定，应从主链路中降级为“后续扩展”，不要在终验时强行展示不稳定能力。

第 106—120 天为终验交付阶段。项目组提交《技术投标文件.docx》《技术评分表.xls》、源代码、源代码说明书、部署说明、测试报告、操作手册、培训材料、项目总结报告和演示视频。终验会议中，项目经理先说明项目建设目标和完成情况，产品负责人演示核心业务链路，技术负责人说明系统架构、接口、部署与安全，测试负责人说明测试结果和缺陷闭环，运维负责人说明部署、备份、监控和后续维护。若老师提出问题，项目组以需求跟踪表和功能响应表为依据回答：已实现功能现场演示，需补充功能说明路线和风险，不属于本期范围的能力说明边界。样例技术规范书要求实施结束后移交全部技术文档，源代码和开发成果也需要交付；本项目在课程场景中同样以“代码 + 文档 + 测试 + 演示”作为完整交付，而不是只提交一份说明材料。

人员分工方面，建议设置项目经理、产品经理、前端负责人、后端负责人、数据与推荐负责人、测试负责人、文档负责人和答辩演示负责人。项目经理负责进度、会议、风险和最终整合；产品经理负责需求、原型、功能响应和用户体验；前端负责人负责 Vue/Uni-app 页面、地图交互、移动端适配和错误状态；后端负责人负责 FastAPI、接口、数据存储、权限和第三方服务；数据与推荐负责人负责 POI 字段、规则模型、报告统计和 AI 解释约束；测试负责人负责编写用例、执行测试、记录缺陷和复测；文档负责人负责投标文件、部署说明、测试报告和用户手册；答辩负责人负责演示脚本、演示账号、演示数据和现场应急。每周至少召开一次例会，关键开发期可采用两天一次短会；每次会议记录决议、问题、负责人和截止时间，避免“大家都知道但没人负责”的情况。通过上述计划，本项目能够在 120 天节奏下完成从 Demo 到可验收工程版本的转化。

## 17 风险分析与应对措施

本项目风险分析按照“数据风险、技术风险、进度风险、安全合规风险、第三方服务风险、用户内容风险、商业闭环风险、验收风险”八类展开。课程 PPT 中关于招投标注意事项强调评分机制应减少主观项，技术评分要细化到可核查证据点，同时付款节点与验收标准应在招标文件阶段明确，以减少后续争议。 因此，本章不写笼统的“加强管理、积极应对”，而是对每类风险说明触发条件、影响范围、预防措施、应急措施和验收证据，使风险管理能够进入项目实施计划和技术评分表。

第一类是钓点与规则数据风险。鱼你有图的核心功能依赖钓点 POI、禁钓规则、常见鱼种、近期鱼获和天气水情等数据。如果钓点数据过少、字段不完整、规则过期或来源不明，用户就无法信任推荐结果。当前项目复核文档也指出，钓点目前仍存在硬编码数据问题，缺少用户共建、纠错、审核与可信度评分，缺少禁钓规则来源、规则更新时间和规则变更通知。 预防措施是建立 POI 数据字段规范，至少包含名称、坐标、类型、来源、更新时间、可钓状态、风险标签和审核状态；对禁钓规则明确来源链接、发布日期、适用范围和更新时间；对用户贡献钓点设置待审核状态，未经审核不得作为强推荐依据。应急措施是当规则数据不确定时，系统不输出“允许垂钓”的确定性结论，只输出“请以现场公告和主管部门规定为准”的风险提示，并降低推荐权重。验收证据包括 POI 样例数据、规则字段说明、数据更新时间展示、风险提示截图和数据来源说明。

第二类是位置隐私与用户信任风险。钓鱼用户对野钓点位置非常敏感，如果平台默认公开精确坐标，可能导致用户不愿记录和分享，甚至引发钓点拥挤、生态破坏和用户纠纷。应对措施是在产品设计中将位置权限作为发布核心字段，支持精确公开、模糊公开、好友可见和完全隐藏；后端根据权限返回不同精度坐标，前端只展示授权后的坐标，不在页面隐藏字段中保留精确坐标；社区信息流默认不展示野钓点精确坐标，只有收费钓场、公开水域或用户主动选择精确公开时才展示。对于历史数据，若用户修改可见性，系统应重新计算展示位置。验收证据包括发布页位置权限截图、不同权限账号看到的位置差异截图、接口返回字段对比和隐私说明文本。

第三类是第三方服务依赖风险。高德地图、天气服务、DeepSeek、日出日落或潮汐接口均可能出现 Key 配置错误、额度不足、网络超时、返回格式变化和服务不可用。一旦前端直接依赖第三方接口，故障会扩大到页面不可用；一旦 Key 写死在前端，又会产生泄露风险。开发设计已经明确第三方 Key 不进仓库，不写死在代码里，前端不直接写死高德 Key 和 DeepSeek Key，而由后端封装。 应对措施是所有第三方接口由后端代理，设置超时、重试、缓存和降级；地图不可用时展示演示 POI 列表，天气不可用时使用最近一次缓存，AI 不可用时只隐藏解释不影响排序，POI 搜索不可用时保留本地专题钓点。验收证据包括 `.env.example`、Key 不入库检查、第三方失败模拟截图、降级提示截图和接口日志。

第四类是推荐与 AI 输出风险。钓鱼推荐涉及安全和合规，如果模型为了提升体验而忽略禁钓、极端天气或危险水域，就会带来实际风险。AI 解释还可能出现幻觉，例如编造不存在的鱼情、政策或钓点评价。应对措施是坚持规则模型优先，AI 只基于后端给出的结构化结果解释，不允许 AI 自行改变排名；推荐输出必须包含总分、分项分、推荐原因、风险提示和相关 POI 数据；禁钓、限钓和安全风险优先级高于距离和热度；AI 提示词中明确禁止编造来源，无法确认时必须提示用户核验。验收证据包括推荐接口响应样例、禁钓水域降权测试、极端天气降权测试、AI 解释 mock 和真实模式对比、提示词约束说明。

第五类是数据持久化与并发风险。当前 MVP 使用 JSON 模拟 NoSQL 数据库，适合课堂 Demo 和单用户演示，但不适合正式多人并发写入。复核文档也明确指出，JSON 文件存储适合比赛 Demo，不适合多人并发写入，正式版本需迁移数据库。 如果继续使用 JSON 承担多人数据写入，可能出现数据覆盖、文件损坏、写入丢失和查询效率低下。应对措施是课程阶段将 JSON 限定为演示数据，同时给出 PostgreSQL/PostGIS 迁移方案；正式版本将用户、记录、帖子、活动、订单等数据迁移至数据库，图片视频进入对象存储；写接口增加事务控制和唯一性校验；关键操作写入审计日志。若课程验收时仍使用 JSON，则应在演示前固定数据、备份数据文件，并避免多人同时写入。验收证据包括数据模型文档、迁移路线说明、备份文件、写入测试结果和数据库方案。

第六类是账号权限与安全风险。当前项目仍存在由前端传入 `user_id` 的风险，正式架构必须由登录令牌识别当前用户，否则可能出现任意用户读取或修改他人记录、报告、私信和活动报名的问题。 应对措施是正式版本引入登录、刷新令牌、当前用户依赖注入、资源所有权校验和管理员权限控制；密码采用安全哈希，不保存明文；敏感接口设置鉴权中间件；日志记录登录失败、异常访问和越权请求；上传文件限制类型、大小和扫描策略；后台管理操作记录审计日志。课程版本若不完整实现登录，也必须在投标文件中明确其为 MVP 待补项，并在演示环境中限制测试账号和数据范围。验收证据包括权限设计说明、接口鉴权测试、越权访问失败截图和安全自查表。

第七类是内容治理风险。社区、评论、私信、群聊和活动都可能出现广告、辱骂、违法信息、虚假鱼获、违规钓点引流和危险活动组织。如果没有审核与举报机制，平台很难长期运行。应对措施是对帖子、评论、图片和群消息预留审核状态、举报入口、拉黑机制和管理员处理流程；对活动发布设置组织者信息、活动地点、时间、人数、安全提示和免责声明；对涉及禁钓区或危险水域的帖子自动提示风险；对虚假钓点和争议内容支持用户纠错和管理员复核。课程阶段可实现基础举报入口和后台审核字段，正式阶段接入内容审核服务。验收证据包括帖子审核字段、举报入口截图、管理员处理流程和活动安全提示模板。

第八类是进度与范围蔓延风险。鱼你有图同时涉及地图、社区、记录、AI、活动、装备、会员和报告，如果没有范围控制，容易在有限实习时间内什么都做一点但主链路不稳定。开发设计书已经明确当前阶段只做 MVP，不做会员系统、赛事系统、复杂商户系统、遥感识别、正式禁渔区数据合作、完整数据库和权限体系、统一登录和多端账号打通等大而全能力。 应对措施是以“地图找点—推荐解释—出钓记录—社区发布—个人报告”为 P0 主链路，活动、装备和会员服务作为可演示闭环，真实支付、监管端、商户后台和遥感识别列入后续扩展。项目经理每周检查新增需求，凡影响终验主链路稳定的需求必须延后。验收证据包括需求优先级表、MVP 范围说明、延期需求清单和版本计划。

第九类是验收表达风险。技术投标文件如果只写“系统先进、体验良好、智能推荐”，但缺少量化指标、测试证据和边界说明，容易被认为不符合实习要求。应对措施是每一项优势都对应可验证证据，例如推荐接口响应时间、记录字段完整率、帖子关联记录比例、报告生成成功率、位置隐私测试、活动报名签到闭环、订单演示闭环、测试用例通过率等。功能响应表中对已实现、部分实现、需补充的功能分开说明，避免把后续规划写成已完成能力。最终提交前由文档负责人检查编号、页眉、字体、表格、引用、目录和附件一致性。验收证据包括技术评分表、功能响应表、测试报告、演示视频和部署截图。

通过上述风险管理，本项目把风险从“答辩时被问到再解释”前移到“投标文件中主动说明并给出措施”。这符合真实工程投标的基本逻辑：风险并不可怕，可怕的是不识别、不分级、不设责任人、不留验收证据。本项目将以风险清单作为项目管理文档之一，在每周例会中更新状态，对高风险项设置责任人和截止时间，对无法在本期解决的风险明确降级策略和后续路线。

## 18 后续扩展规划

本项目后续扩展遵循“先稳主链路，再扩数据层；先做可信记录，再做复杂交易；先做用户价值，再做平台生态”的原则。当前版本已经能够支撑“先记录、再连接、后服务”的核心叙事，包括一键开竿、定位、天气、收竿汇总、鱼获记录、社区关联、活动提醒、活动报名、装备入口和会员报告等演示能力。 但是，复核文档也明确指出，真实上线仍需完成登录鉴权、审核、支付、数据库迁移、对象存储、WebSocket 和更完整的数据备份监控。因此，后续扩展不应把所有功能一次性堆上去，而应按数据与安全、地图与规则、社群实时化、商业闭环、公共服务和智能分析六条路线逐步推进。

第一阶段是数据与安全底座升级。当前 JSON 文件适合课程 Demo，但正式多人使用必须迁移到 PostgreSQL/PostGIS、Redis 和对象存储。PostgreSQL/PostGIS 负责保存空间 POI、用户记录、鱼获明细、帖子、活动、订单和报告快照，支持空间索引、范围查询、附近钓点检索和热力统计；Redis 负责缓存天气、热门钓点、推荐结果、登录会话和验证码；对象存储负责图片、视频、头像、报告长图和活动附件。账号系统方面，引入手机号/微信授权登录、刷新令牌、用户资料、角色权限和资源所有权校验，避免前端传入 `user_id` 带来的越权风险。安全方面，引入日志脱敏、操作审计、位置权限分级、数据导出删除机制和备份恢复演练。该阶段的目标不是增加用户看得见的新功能，而是让系统从“可演示”变成“可多人使用、可长期保存、可追责恢复”。

第二阶段是地图与钓点数据增强。鱼你有图的核心壁垒在垂钓语义增强 POI，因此后续需要建立钓点共建、纠错、审核和可信度评分机制。用户可以提交新钓点、补充鱼种、上传环境照片、标记收费信息和规则变化；平台根据用户等级、历史记录真实性、其他用户反馈和管理员审核结果计算数据可信度。禁钓、限钓和安全规则需要建立来源字段、发布日期、适用范围和更新时间，并支持规则变更通知。热力图也需要从简单活跃度扩展为按鱼种、钓法、季节、时间段和天气条件筛选。例如用户选择“路亚 + 翘嘴 + 傍晚”，系统展示近期相关记录热力，而不是展示所有鱼获热力。对海钓场景，扩展潮汐、浪高、风浪、船次、船长、费用、安全确认和返航时间等字段；对城市近郊野钓场景，扩展停车、夜钓、岸线安全、垃圾点和厕所等字段。该阶段的目标是让地图从“钓点展示”升级为“垂钓决策图层”。

第三阶段是社群实时化与内容治理。当前社区和群聊若主要采用普通 HTTP 刷新，适合演示但不适合真实社交。后续应引入 WebSocket 或消息推送服务，实现私信、活动群聊、未读数、已读状态、消息撤回和图片消息。好友关系从演示用即时通过升级为申请、接受、拒绝、拉黑和举报流程；社区信息流从静态或简单排序升级为关注流、同城流、话题流和钓点关联流；评论、点赞、收藏、关注、举报和屏蔽全部持久化。内容治理方面，建立帖子审核、图片审核、敏感词过滤、用户举报、管理员处理和违规记录机制。对于涉及禁钓区、危险水域或可能诱导违规捕捞的内容，系统自动添加风险提示或限制传播。该阶段的目标是让结构化社区从“能看能发”升级为“能互动、能沉淀、能治理”。

第四阶段是活动与商业闭环正式化。当前项目已经具备活动报名、取消报名、签到、活动履历、从活动生成出钓记录和订单演示闭环，但真实支付、退款与商家结算仍未接入。 后续可将活动模块扩展为同城约钓、钓场比赛、俱乐部活动、新手训练营和亲子垂钓体验，支持报名审核、名额管理、费用支付、签到核验、活动群、活动评价和安全事件反馈。装备服务扩展为商家认证、商品管理、购物车、订单、支付、退款、售后和佣金结算；装备推荐不只基于广告位，而是基于用户真实记录中的钓法、鱼种、装备使用次数和代表战绩。会员服务从报告生成扩展为月报、年报、生涯报告、钓法效率分析、空军复盘、个人成长建议和同城活动优先报名。该阶段的目标是让商业化建立在真实记录和真实关系之上，而不是简单依赖广告和流量售卖。

第五阶段是公共服务与监管协同。钓鱼不仅是兴趣活动，也涉及生态保护、禁捕禁钓、安全管理和公共水域秩序。后续平台可以为地方水域管理方、渔政部门、钓场经营主体和文旅单位提供轻量化管理工具。例如公共水域规则可视化、违规高风险区域提醒、文明垂钓积分、钓点垃圾反馈、安全隐患上报、活动备案、钓场经营数据看板等。对用户端，平台只展示通俗易懂的“可钓、限钓、禁钓、注意安全”提示；对管理端，平台提供规则配置、公告发布、用户反馈处理和空间热力分析。该方向需要严格处理数据合规和政府合作边界，不应在课程版本中承诺已经具备正式监管能力，而应作为后续可拓展方向。其价值在于将“能不能钓”的用户需求与“如何规范休闲垂钓”的公共管理需求连接起来。

第六阶段是智能分析与算法优化。当前推荐以规则模型为主，AI 做解释，这是 MVP 阶段正确选择。后续当记录数据积累后，可以逐步引入更精细的个性化推荐和因果分析，但仍需保持可解释和可控。例如基于用户历史记录预测不同天气、时段、水域类型下的上鱼概率；基于同城相似用户发现适合新手的钓点；基于空军记录推荐调整钓法、饵料或时间段；基于装备使用记录评估装备适配场景；基于报告结果推荐教程、活动和服务。算法评估指标可以包括推荐点击率、出钓后记录率、用户采纳率、推荐后上鱼率、空军复盘完成率和报告转化率。AI 解释仍然只解释结构化结果，不直接编造事实。对于模型偏差，需要允许用户反馈“推荐不准、规则错误、钓点关闭、鱼种不符”，并将反馈进入数据更新流程。该阶段的目标是把“经验判断”逐步升级为“数据驱动但可解释的垂钓辅助决策”。

后续扩展的时间安排建议分为三个版本。V1.0 面向课程验收和小范围演示，目标是稳定主链路，完成地图、推荐、记录、社区、报告、活动和订单演示，提供部署说明、测试报告和演示数据。V1.5 面向小范围真实用户试点，目标是完成登录鉴权、数据库迁移、对象存储、真实高德服务、位置隐私、内容举报和基础监控，选择武汉或长江经济带某一城市进行数据验证。V2.0 面向商业化验证，目标是完善同城活动、会员报告、教程推荐、商家认证、订单支付和活动安全管理。V3.0 面向平台生态，目标是形成钓点共建审核体系、监管协同接口、B 端经营工具和跨城市复制能力。每个版本都应有明确的验收指标，避免用“持续优化”代替具体计划。

需要强调的是，后续扩展不是对本期投标范围的无限追加。按照工程投标文件的写法，本期承诺应聚焦 MVP 和课堂验收要求，后续规划只说明技术路线、扩展边界和演进方向。对真实支付、正式监管合作、大规模数据库、第三方安全测评、CNAS 测试报告等能力，如果课程项目无法实际完成，应表述为“正式工程化阶段实施”，不能写成当前已具备。这样的表达既能体现项目想象力，也能保持投标文件的真实性和可验收性。
